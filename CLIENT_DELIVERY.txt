## 1. System Overview

A Node.js middleware application acts as a bridge between HubSpot CRM and TripleSeat event management. It runs on Google Cloud Run and listens for webhooks from both platforms, keeping deals and events in sync in both directions.

```
HubSpot  ──── webhook ────▶  Middleware  ────▶  TripleSeat
HubSpot  ◀─── API call ────  Middleware  ◀────  TripleSeat
```

**Live URL:** `https://tripleseat-831689172447.europe-west1.run.app`

---

## 2. Integration Flow

### Direction 1: HubSpot → TripleSeat

```
1. Agent updates a HubSpot deal and sets tripleseat_push = Yes
2. HubSpot workflow fires a webhook to the middleware
3. Middleware fetches the full deal from HubSpot API
4. Middleware fetches associated contact(s) from HubSpot API
5. For each contact:
     - Search TripleSeat by email
     - If found  → update the existing TripleSeat contact
     - If not found → create a new TripleSeat contact
6. For the primary contact:
     - If tripleseat_event_id is blank → create a new TripleSeat event
     - If tripleseat_event_id is set   → update the existing TripleSeat event
7. After first-time creation, the new TripleSeat event ID is written back
   to the HubSpot deal as tripleseat_event_id (cross-system link)
```

### Direction 2: TripleSeat → HubSpot

```
1. Any field on a TripleSeat event is updated (amount, status, date, etc.)
2. TripleSeat fires a webhook to the middleware
3. Middleware looks up the linked HubSpot deal via tripleseat_event_id
4. If a deal is found, changed fields are synced back to HubSpot
5. Only fields that have actually changed are written (no unnecessary updates)
```

## 3. Trigger Points

### HubSpot → TripleSeat Trigger

| Setting | Value |
|---|---|
| Property | `tripleseat_push` |
| Trigger value | `Yes` (true) |
| How to use | Set this property to Yes on any deal to push it to TripleSeat. Set it again to re-sync updates. |

After the sync completes, the middleware does **not** automatically reset `tripleseat_push` back to No. To re-sync an updated deal, the agent must set it to Yes again.

### TripleSeat → HubSpot Trigger

The middleware receives automatic webhooks from TripleSeat on:
- **Update Event** - any field change on a TripleSeat event
- **Delete Event** - event deletion (currently logged, no HubSpot action taken)

## 5. Property Sync - TripleSeat to HubSpot

These fields are synced back to the HubSpot deal when a TripleSeat Update Event webhook fires.

| TripleSeat Field | HubSpot Property | Notes |
|---|---|---|
| `status` | `dealstage` | Mapped via reverse stage mapping. TENTATIVE and PROSPECT only update if deal stage changes. |
| `actual_amount` | `amount` | Only synced if value is > 0 and differs from current |

| `description` | `event_details` | Additional Information field |

### HubSpot Webhook (HubSpot → Middleware)

| Setting | Value |
|---|---|
| Endpoint URL | `https://tripleseat-831689172447.europe-west1.run.app/webhook/hubspot` |
| Method | POST |
| Trigger | Property change: `tripleseat_push` = `true` |
| Setup location | HubSpot → Workflows → [Your Workflow] → Webhook Action |

**Steps to configure in HubSpot:**
1. Go to Automation → Workflows
2. Create or edit a deal-based workflow
3. Set enrollment trigger: Deal property `tripleseat_push` is equal to `true`
4. Add action: Send webhook → POST to the URL above
5. Enable re-enrollment so the workflow fires again when the property is set again

| Setting | Value |

| Trigger Actions | Update Event |
| Signing Key | Set in TripleSeat and stored in env as `TRIPLESEAT_SIGNING_KEY` |
| Setup location | TripleSeat → Settings → Webhooks → Add Webhook |

**Steps to configure in TripleSeat:**
1. Go to Settings → Webhook Endpoints
2. Click Add Webhook

## 12. TripleSeat Configuration

### API Authentication

TripleSeat uses OAuth2 client credentials. The middleware automatically requests and caches tokens, refreshing before expiry.

- Client ID: stored in `TRIPLESEAT_CLIENT_ID`
- Client Secret: stored in `TRIPLESEAT_CLIENT_SECRET`
- Token endpoint: `https://api.tripleseat.com/oauth/token`

### Contact Deduplication

Before creating a contact in TripleSeat, the middleware searches by email using `GET /v1/contacts/search.json?query={email}`. If a match is found, the existing contact is updated. No duplicates are created.

## 13. Deduplication Logic

### Event Deduplication

After the first sync, the TripleSeat event ID is stored on the HubSpot deal (`tripleseat_event_id`). On all subsequent syncs:

- If `tripleseat_event_id` is **blank** → create new event
- If `tripleseat_event_id` is **set** → update existing event

This prevents duplicate events from being created if the workflow fires multiple times.

### Contact Deduplication

- Search TripleSeat for the contact by exact email address
- If found → update name and phone with latest HubSpot data
- If not found → create new contact

## 14. Known Limitations and Pending Items

| Item | Status | Notes |
|---|---|---|
| Booking block | Commented out | The `booking` sub-object (status + source) is disabled. Re-enable when ready by uncommenting in `tripleseatService.js` |
| Event end time | Auto-calculated | TripleSeat `event_end` is set to `event_start + 1 hour`. No dedicated end time field is mapped from HubSpot. |
| Event start time | Current wall-clock time | Since HubSpot only stores a date (no time), `event_start` uses the server's current time at the moment of sync. On updates, the original time is preserved unless the date changes. |
| `guest_count` field name | To be confirmed | The TripleSeat webhook payload field for guest count has not yet been confirmed from a live payload. The middleware reads `guest_count`. |
| TripleSeat auth unhealthy | Needs fix | Cloud Run env vars `TRIPLESEAT_CLIENT_ID` / `TRIPLESEAT_CLIENT_SECRET` appear missing or incorrect. Confirm these are set under Cloud Run → Edit → Variables. |
| Lead source reverse sync | Commented out | Syncing `selected_lead_sources` back from TripleSeat to HubSpot is currently disabled. Can be re-enabled in `tripleseatController.js`. |
